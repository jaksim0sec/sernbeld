## 목표 아키텍처
1. 입력 공급자: named(명시적인 NPC별 authored 그래프), personal(역할/성격/지역/일과/관계 기반 짧은 범용 그래프), event(현재 사건과 당사자/알려진 사실을 바인딩한 그래프). 기존 서비스 행동은 별도 handler registry로 유지. 세 공급자는 동일 ConversationInstance를 생성한다. 여기서 생성형은 등록 데이터와 사실의 조합 및 조건에 따른 구성이지 외부 LLM 호출이나 자유 텍스트 추론이 아니다. LLM 없이 오프라인 동작.
2. Topic resolver: NPC별 entry 및 관계/일과·사건 조건 평가. 첫 인사 자격을 기존 met에서 읽고, 명시적으로 중요한 개인 대화가 있으면 우선; 진행 중인 합류 가능한 그룹은 현재 화제를 안내; 그 외 시작 대사와 실제 관련 사건 화제를 함께 제시한다. 이벤트가 있다는 이유로 모든 개인 대화를 덮어쓰지 않는다. 일반/고유 화제, 사건별 화제, 직업 서비스, 종료를 구별. 해당 NPC 개인 등록이 없을 때만 해당 화제에 personal fallback, 조건 불충족/빈 템플릿일 때 안전한 짧은 인사 또는 종료. 유명 NPC는 고유 정의, 대다수 주민은 범용 정의 재사용.
3. Conversation runner: UI와 분리된 단일 상태 기계가 현재 노드, 발화 순서, 응답, 화제 전환과 결과를 소유. UI는 기존 패널·이름표·타이핑·토큰·종료 기능 재사용. 사용자 응답을 고정된 선택지로 한정하고 다음 노드를 평가; 일반 대사/특수 사건/서비스 결과가 같은 세션 안에서 이어진다.
4. Domain bridge: 사건, 지식, 의뢰, 경제, 관계의 권위는 기존 living-world/Society/Inventory/Save에 유지. 대화 엔진은 조건 조회, 안전한 바인딩, 허용된 명령 요청과 결과 분기만 수행. 대화 문장이나 임의 JSON payload가 재화·지식·관계를 수정하지 않는다.

## 데이터 계약 제안
TemplateDefinition: {id, version, source: named|personal|event, topicId, priority, eligibility:{npcIds?,regionIds?,roles?,tags?,conditions[]}, slots:[{id,kind: npc|player,tags?,role?}], eventBinding?:{typeId,factRefs:[{alias,slotId,factKey}]}, entryNode, nodes, cooldown?, memoryPolicy?}. 안정 ID/버전, 지역·역할·슬롯/사건 타입을 기존 registry에서 검증. 개인은 NPC+player, 그룹은 기존 2~4명 NPC 슬롯에 player 추가. source는 선정 경로이지 별개 실행기 아님.
Node: {id, type: speak|choice|effect|end, speakerSlot?, pages?:string[], next?:nodeId, choices?:[{id,label,conditions[],nextNode}], action?:{handlerId,argsRefs}, outcomes?:{ok:nodeId,fail:nodeId,stale:nodeId}}. speak는 문장/배열 및 다음 진행, choice는 조건 통과 응답만 표시, effect는 명시적 응답으로 진입한 경우만 실행, end는 topicHub/close 중 하나. 모든 참조 유효·도달 가능한 종료/복귀 경로, 자동 전이 순환 금지; 의도된 사용자 입력 루프에는 종료 선택 보장. 텍스트 렌더는 기존 textContent, 허용된 placeholder만 치환. 이벤트의 비공개 사실은 화자 slot의 knowledge 및 revision이 증명할 때만 노출.
Condition: 허용 목록의 typed predicate(e.g. met, role/tag, activity, affinityGte, questState, eventActive, knowsFact, choiceSeen, topicSeen, actionAvailable), all/any/not 조합. eval/임의 함수/문장 기반 추론 금지. 등록 시 arity·타입·ID 검사, 실행 시 최신 읽기 전용 상태 사용. 알 수 없는 조건/바인딩은 실패 안전.
ConversationInstance(휘발): {sessionId, templateId, templateVersion, topicId, anchorNpcId, participants/slotBinding, eventRef?:{id,revision}, nodeId, pageIndex, phase, selectedChoiceIds, activeTurn, localVars, revision, holdToken}. topicHub 복귀 시 세션 참여자 유지, 이전 화제의 이벤트 사실은 새 화제로 무단 전파 금지. 저장에는 인스턴스 전체를 넣지 않는다.
ConversationMemory(영속, Save NPC 안정 ID): 기존 met/talks/lastTalk/lastAction 보존, 필요한 authored flag/topic completion/cooldown 및 최근 의미 있는 선택만 가산. 일반 대사 열람/자동 말풍선으로 친화도 증가 금지. 제안 상한은 NPC당 최근 선택 16건, 내용 아닌 ID/시점 저장, 명시적인 지속 플래그는 등록된 키만 허용. 이벤트 사실은 기존 world knowledge에서 참조하며 복제하지 않는다. 저장 버전/이전 데이터 호환 및 rollback 검증. 재로드는 진행 UI 복원보다 안전 종료/hold 해제 후 다시 화제 선정.

### 예시 (설계 fixture, 신규 실콘텐츠 아님)
- 고유 NPC: 첫 인사 2페이지 → [항구에 대해 묻기 / 이곳에서 할 일 / 거래] → 각자 다른 응답 노드 → [더 묻기 / 다른 이야기 / 종료]. 이전 선택을 기억하는 후속 노드는 choiceSeen 사용. 첫 인사 이후에도 사용자 응답으로 일반 주제에 진입 가능.
- 일반 주민: 일과가 근무이고 직업이 부두 일꾼인 NPC에 personal.docker.work 적용 → [오늘 일은 어때요? / 마을에 대해 / 종료] → 해당 답변·후속 질문. 고유 대화 등록이 필요하지 않다.
- 사건: 가상의 공급 지연 사건 E/rev3, 알려진 품목·장소를 실제 사실 슬롯으로 구성 → [무슨 일이에요? / 도울 수 있나요? / 다른 이야기] → 질문은 해당 화자가 아는 사실만 발화, 도움은 기존 의뢰 조회 및 수락/실패 결과 노드, 사건 해결/갱신 시 이전 선택은 stale 노드로 전환. 미발생 사건은 표시되지 않음. 직접 대화와 NPC 간 담화가 같은 event ID/revision과 사실 참조를 공유. 단순 이야기 선택은 사건 해결이 아니다.

## 진행 및 상태 전이
idle → acquire(접근/대화 가능/그룹 hold 검증) → topicHub 또는 speak → advancing(페이지/턴) → awaitingChoice → resolving(재검증/효과 실행) → speak/choice/topicHub/end. 세션 ID+revision+node ID+choice ID+필요한 도메인 quote로 입력 식별; 중복 클릭 및 이전 화면 콜백 거절. 렌더 갱신은 closeSpeech를 호출하지 않으며 실제 종료만 hold 해제. 실행 전 최신 접근/사건/슬롯/조건/경제 검증, 실행 결과에 따라 노드 분기. 실패 시 설명+유효한 선택지 갱신, 성공 시 효과 및 완료 기억의 중복 기록 방지. 모든 자동 전이는 상한(제안 32회)을 적용하고 실패 안전. UI 패널 닫기/Escape/지역 이동/거리 이탈/참여자 소실/실패에서 동일 종료 경로로 hold를 정확히 한 번 해제; resume 실패는 기존 retry 재사용. 종료/새 주제/타이핑 중 클릭의 의미를 별도 테스트.
- event revision 변경: 동일 revision이면 계속; 변경·종료 또는 knowledge 소실 시 더 이상 stale 문장/효과를 내지 않고 최신 사실로 재선정하거나 사건 종료 안내 → topicHub. 선택이 영향을 주는 사건 revision은 도메인 커밋 결과로 다시 읽음.
- 개인 대화 상태와 사건 상태를 하나의 context에 넣되 독립된 topic ID로 관리. 이전 주제 재개는 해당 템플릿의 명시적 규칙이 있을 때만; 모든 대화를 장기 기억하는 시스템은 범위 밖.
- 서비스 행동은 기존 Society의 상점/길드/숙박/의뢰/그룹 명령을 adapter로 노출. 기존 행동 효과를 복제하지 않음. 구형 say 호출은 legacy linear adapter를 통해 점진 이관. 인사/거래 등 실제 기존 후속 응답을 이관한 뒤 회귀 확인.

## NPC 간 담화와 성능
- 기존 근접 그룹 매칭, 지역/역할/태그, 최대 4 NPC, 이동 여부, 스케줄 pauseable 및 거리 LOD 보존. 먼 그룹에는 ···, 가까울 때만 해당 context를 materialize; 비참여 발화는 페이지/기억/효과를 소비하지 않음. 비참여는 동일 템플릿의 명시적 ambient path(선형 turn/무효과)만 실행. 참여 시 실제 현재 turn/node와 진행 offset을 넘겨 필요한 앞 맥락만 제공. 앵커 NPC의 첫 대사를 다시 출력하지 않음. 그룹 전체 hold 인계와 이탈 시 재개 보존.
- 후보 선정은 상호작용/사건 변경/기존 LOD 진입 같은 트리거에 한정; 지역+역할+사건 타입 인덱스, 후보 점수와 안정 tie-break, 최근 화제 cooldown을 이용해 단조 반복 완화. 사건 후보는 해당 주민/알고 있는 사건으로 한정. 매 프레임 전체 템플릿·전체 NPC·이벤트 순회, 외부 API 호출 금지. 현재 50명 카엘과 100/300/1000 논리 NPC fixture, 2ms p95/4ms slice·10% 회귀 기준(실기기와 별개), 오프라인 동작 확인.

## 콘텐츠 생산 정책 보강 (2026-11-25)
사용자 방향: 전 주민의 개별 대사를 작성하지 않는다. 주요 인물만 고유 서사와 화제를 직접 작성하고, 개별 등록이 없는 주민은 기존 템플릿의 개인 대화 확장으로 짧은 일상 대화를 제공한다. 이벤트는 일반 대화의 대체가 아닌 독립 화제다. 기존 NPC-003 공용 resolver/runner를 활용하며 별도 엔진을 만들지 않는다.

### 선정 및 데이터
- 기존 NPC ID·역할·지역·일과·태그를 재사용한다. 성격 태그와 고유 화제 참조는 선택 사항이다. 주요 NPC는 고유 화제의 등록 여부로 표현하며 유명도 수치 시스템은 추가하지 않는다.
- 범용 개인 템플릿은 TemplateDefinition의 source=personal 및 NPC 1명+player 슬롯을 사용한다. 안정 ID, topicId, 적용 역할/태그/지역/활동 조건, 짧은 발화 노드, 선택적 질문과 후속 답변, 종료/화제 복귀를 등록한다. eventBinding 없이 성립하며 기존 그룹 2~4명 제약을 개인 슬롯에 강제하지 않는다.
- 첫 만남의 기존 고유 인사 우선. 각 화제에서 적격 고유 대화 > 역할/성격/현재 일과 기반 개인 템플릿 > 지역 공통 템플릿 > 안전한 짧은 인사 순으로 fallback한다. 고유 NPC도 미작성 화제에는 범용을 사용한다. 같은 topicId의 고유/범용 중복은 숨긴다.
- 현재 사건 화제는 영향 범위·실제 지식·revision 검증 후 별도로 노출한다. 직업 서비스와 의뢰 역시 독립적으로 기존 조건을 검증해 노출한다. 개인 발화 미등록이 그룹 참여나 서비스 진입을 막아서는 안 된다.
- 범용은 한두 문장과 필요시 1~2개 응답, 짧은 후속 답변 정도를 초기 작성 지침으로 삼는다(강제 스키마 제한 아님). 고유는 기존 다중 페이지와 분기를 허용한다. 일반 대화를 억지로 의뢰나 보상으로 연결하지 않는다.
