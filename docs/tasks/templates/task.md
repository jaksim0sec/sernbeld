# AREA-000 작업 제목

- 목표와 완료 기준
- 기준 브랜치와 시작 SHA
- 구현 단계 / 검증 범위 / 사용자 승인 범위
- 변경 경로와 보존 대상
- 계약, 의존 작업 ID, 병렬 변경과 충돌 가능 경로

| 요구/보존 기준 | 검증 명령 또는 방법 | 결과와 증거 |
| --- | --- | --- |

- 결정·남은 한계·다음 행동

다단계 작업은 필요한 경우에만 추가한다. S 0~1T / M 1~3T / L 2~4T가 기본이며 초과 시 구체적 근거를 적는다. 조사·구현·검증·커밋을 절차별 T로 나누지 않는다. [T 분할과 진행 기준](../INDEX.md#t-분할과-진행-기준) 및 [검증 정책](../../validation/VALIDATION_POLICY.md#단계-검증과-최종-게이트)을 따른다.

- 전체 작업 최종 게이트(필요한 경우): 검증 대상·필수 여부·실행 환경·증거·남은 범위. 모든 T에 같은 CI/배포/실기기 조건을 복제하지 않는다.

작업 주소: `AREA-000/T1` (단계 ID는 작업 내부에서 고유하게 유지)

## T1 단계명

- 목표 / 완료 기준 / 선행 단계
- 구현 및 변경 근거
- 해당 T의 직접 필수 검증 및 결과(PASS·FAIL·PARTIAL·NOT RUN)·증거 / 승인 범위
- 다음 T를 실제로 막는 의존성(없으면 없음); 최종 게이트 대기와 구분
- 미완료 범위 / 다음 작업 주소

새 단계는 `T2` 등 새 ID로 추가한다. 상세 단계 기록은 Markdown에 남기고 구조화 기록의 `next`는 다음 작업 주소와 남은 행동을 함께 적는다. 기존 기록의 단계 ID는 보존한다.

## 반복 제작 비용을 측정할 때

요청부터 실제 게임 통합·검증까지 걸린 시간, 제작 환경 준비 횟수, 사용자 교정 횟수, 반복 문제, 통합 뒤 회귀, 사용 토큰(확인 가능하면)을 기록한다. 동일 유형·비슷한 난도의 이전 결과에서 같은 단위를 취하고 측정 불가 값은 비워 둔다. 예상 배율은 실측과 구분한다.
