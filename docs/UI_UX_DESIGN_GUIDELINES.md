# 세른벨드 UI/UX 개발 전 설계 지침서

> 버전: v0.2  
> 적용 범위: 세른벨드의 모든 신규 UI 및 기존 UI 개편  
> 디자인 기준 구현: 캐릭터 생성 UI (`src/entities/character/studio-ui.css`)
> 공통 SEED: [`styles/seed.css`](../styles/seed.css) / 메인 UI 호환 토큰: [`styles/tokens.css`](../styles/tokens.css)  
> 목적: UI 구현 전에 기능·콘텐츠·사용자 행동·계층 구조를 먼저 설계하고, 구현 후에는 디자인 시드와 실제 사용 경험을 기준으로 검토한다.

## 디자인 SEED 기준

- 캐릭터 생성 UI가 기준 구현이다. 새 시스템 UI의 색상·타이포·상태·아이콘·모션은 여기서 추출한 공통 SEED를 사용한다. 예전 Luminous Field 청록/남색 시스템 팔레트는 표준이 아니다.
- 네 단계 무채색 표면(#101010, #181818, #262626, #363636)과 흰색/회색 글자 대비로 위계를 표현한다. 일반 버튼·카드에는 보더나 글로우를 기본값으로 두지 않는다.
- 독립 조작은 원형/알약형, 선택 카드와 탭은 기준 구현의 라운딩·상태를 사용한다. 선택은 흰색/검정 대비 또는 밝아진 회색 표면으로 표현하며, 선택 규칙은 컴포넌트 역할에 따라 일관되게 적용한다.
- 제목은 1.35rem/780/-0.045em, 일반 버튼은 .8rem/650/-0.02em, 최소 터치 영역은 2.75rem을 기준으로 한다. SVG는 둥근 끝과 접합부, 24 단위 뷰박스에서 1.8 스트로크를 기준으로 한다.
- 버튼의 색상 전환 200ms, 누름 180ms/0.97배, 시트 전환 360ms의 기준 모션을 사용하고 reduced-motion을 존중한다. 여백은 콘텐츠와 행동의 관계를 구분할 때만 사용한다.
- 재화는 독립 알약형 표시 컴포넌트로 제공한다. 메인 메뉴는 게임 관리용이고 가방 등 인게임 도구는 분리한다.
- 월드·캐릭터·아이템·지도 지형·마법진은 게임 콘텐츠이므로 자체 색을 보존한다. HUD와 월드 오버레이는 가독성을 위해 투명도와 최소한의 경계를 사용할 수 있다.
- 기존 개별 메뉴의 레이아웃 및 남은 로컬 스타일 개편은 한 화면씩 검토하고 승인받아 진행한다. 공통 SEED 변경이 전체 메뉴 개편 완료를 뜻하지 않는다.

## 기본 원칙

- UI로 명확히 표현해야 할 것은 UI로 표현한다. 세계관 연출을 모든 인터페이스에 강제하지 않는다.
- 반투명·홀로그램·마법진은 목적에 맞는 표현 수단이지 공통 필수 규칙이 아니다.
- 게임 세계에 몰입하는 경험과 UI 자체를 사용하는 경험을 모두 중요하게 다룬다.
- 컨테이너, 장식, 여백, 제스처는 각각 설명 가능한 이유가 있어야 한다.
- 기존 기능과 캐릭터 모델을 보존하면서 정보 구조와 조작 경험을 개선한다.

## A. 계획: 구현 전

### A1. 기능과 콘텐츠

- [ ] 사용자의 최종 목표 행동은 무엇인가?

### A2. 사용자 행동 경로
- [ ] 진입 직후 무엇을 할 수 있는지 이해되는가?

- [ ] 단계 순서가 자연스러운 사고 흐름과 맞는가?
- [ ] 자주 하는 행동에 불필요한 전환이나 조작이 없는가?
- [ ] 취소·되돌리기·완료 경로가 명확한가?

### A3. 우선순위와 가중치
- [ ] 핵심 콘텐츠·주요 행동·보조 기능을 구분했는가?
- [ ] 중요도와 사용 빈도에 맞는 접근성·시각적 비중을 부여했는가?
- [ ] 크기·대비·위치·여백이 중요도를 드러내는가?
- [ ] 모든 요소를 똑같이 강조하거나 약하게 만들지 않았는가?

- [ ] 홀로그램·반투명·마법진이 가독성과 조작성을 해치지 않는가?

- [ ] 세계 몰입과 UI 사용 경험을 모두 존중하는가?

## C. 계층구조 설계가 약한 에이전트의 필수 작업 절차

1. **콘텐츠 목록 작성:** 필요한 정보·행동·상태를 나열한다. 이 단계에서는 컨테이너와 배치를 정하지 않는다.
2. **중요도·관계 분석:** 핵심·보조·부가 요소를 분류하고 부모·자식·동등 관계를 정한다.
3. **계층 트리 작성:** 텍스트 기반 트리를 먼저 만든다. 모든 그룹의 기능적 이유를 명시한다.
4. **레이아웃 설계:** 시선 흐름·조작 빈도·화면 크기에 따라 위치와 비율을 정한다.
5. **디자인 시드 적용:** 검증된 구조 위에 컴포넌트·색상·장식·애니메이션을 적용한다.
6. **실제 화면 검토:** 코드가 아니라 최종 화면을 보고 A·B 항목을 검사한다.
7. **제거·단순화 검증:** 존재 이유가 불명확한 컨테이너·장식·조작 단계·여백을 재검토한다.

### 에이전트 제출물
- 핵심 기능과 필수 콘텐츠 목록
- 주요 사용자 행동 경로
- 우선순위 및 계층 트리
- 게임 요소/UI 요소 분류 근거
- 실제 화면과 체크리스트 검토 결과
- 남은 문제 및 검증하지 못한 사항

## D. 최종 자기비판

- **제거 검증:** 이 요소를 제거하거나 단순화하면 사용 경험이 실제로 나빠지는가?
- **대안 비교:** 다른 구조를 최소 하나 고려했고, 현재 구조를 선택한 이유가 있는가?
- **초심자 검증:** 제작자의 설명 없이 처음 사용하는 사람이 핵심 행동을 발견하고 완료할 수 있는가?

체크 표시만으로 통과시키지 않는다. 근거가 부족하거나 실제 화면에서 문제가 발견되면 다시 설계한다.

## E. 첫 적용: 캐릭터 생성 UI

- 캐릭터 미리보기와 설정 조작 영역의 역할을 구분한다.
- 얼굴·체형·색상·파츠·프리셋 등 실제 제공 기능을 먼저 조사한 후 구조화한다.
- 캐릭터 모델·기존 기능은 보존하고 UI 정보 구조와 조작 경험을 우선 개선한다.
- 여기서 검증된 시각 언어와 컴포넌트를 다른 화면에 확장하되, 모든 화면에 동일한 레이아웃을 강요하지 않는다.

**판단 기준:** 화려함이나 투명도보다 사용 목적, 계층구조, 조작의 명확성, 게임과의 조화를 우선한다.
